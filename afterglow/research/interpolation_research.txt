Интерполяция, экстраполяция и время записей GameSense / Source 1
Дата разбора: 23.11.2026

ОБЛАСТЬ И ДОСТОВЕРНОСТЬ

Исследована предоставленная skeet.dll, SHA256:
052e177d5c79b9fdbac938f73d629e2ca70467353bcd90eb67000eba91f8d4c2.
Это сборка с внешней оболочкой; её нельзя автоматически считать неизменённым
официальным GameSense. Из ресурса извлечено ядро binary.bin размером 3129344
байта; использован адресный диапазон с базой 0x43310000. DLL не запускалась.
Lua, DLL и опубликованный рабочий Afterglow не изменялись.

Исследование статическое. Ниже разделены:
А — непосредственно наблюдаемые инструкции этой сборки;
Б — интерпретация их назначения, требующая подтверждения указателей/вызовов;
В — поведение открытого Source SDK, служащее сравнением, а не доказательством
полной идентичности конкретной версии CS:GO.

Полностью восстановить ВСЮ внутреннюю экстраполяцию скита и живые значения
по умолчанию по одному этому файлу не удалось. Отсутствуют исполняемые модули
именно твоей игры и снимок состояния на сервере; часть связей обфусцирована.
Наличие бинарника не даёт исходников или полного перечня реально действующих
настроек. Неустановленные детали далее явно отмечены.

ТРИ РАЗНЫХ МЕХАНИЗМА

1. Интерполяция движка: отображение удалённых объектов по истории сетевых
   состояний с задержкой. Это не локальный prediction своего движения.
2. Экстраполяция движка: продолжение изменения некоторых переменных, когда
   данных для интерполяции больше нет, при выполнении дополнительных условий.
3. Работа чита с записями: выбор времени, проверка допустимости, построение
   промежуточного состояния и работа с анимациями/геометрией для выстрела.
   Включённая экстраполяция картинки не доказывает использование этого же
   прогноза при сканировании противника.

ПОДТВЕРЖДЁННЫЕ УЧАСТКИ ЯДРА

1. 0x4331E237–0x4331E2C8: три чтения из объектов формы ConVar, обход родителя
   по +0x1C, получение float из +0x2C с XOR адреса объекта. Результат:
       F = max(B, C / A)
   Максимум реализует проверенный вспомогательный код 0x4332FC35.
   По формуле и другим местам использования A/B/C с высокой вероятностью
   соответствуют cl_updaterate / cl_interp / cl_interp_ratio. Это вывод Б:
   привязка имён к зашифрованным указателям в работающем клиенте не проверена.
   В самой функции нет явного ограничения ratio серверными min/max cvar.
   Возможные ограничения в других местах этим не исключаются.

2. 0x43320386–0x4332039A: оболочка вызывает указанную функцию и возвращает
       max(F, G)
   Начальное G по адресу 0x43469254 равно 0.015625 секунды. Следовательно,
   этот путь имеет дополнительную нижнюю границу 15.625 мс. Это не означает,
   что каждый путь ядра использует оболочку: есть прямые вызовы F.
   В 0x433243BF–0x43324427 также видны вычисление максимума с G, прибавление
   отдельной сетевой величины и ограничение результата диапазоном 0..0.2.

3. 0x433207A1–0x43320941: ветки зависят от аргумента внешнего вызова.
   В одной в два объекта записывается округлённое 1/tickinterval; в другой
   используются 64. В объект B записывается float 0.015625, в C — integer 2;
   G устанавливается в 0.015625. Есть временные изменения служебных полей
   ConVar вокруг записи. 0x4341F6B8–0x4341F719 содержит похожий набор
   присваиваний под условием внешнего интерфейса. Эти значения А; назначение
   имён A/B/C и смысл событий — Б. Это не универсальные заводские defaults
   всех версий GameSense и не подтверждённый активный профиль твоего сервера.
   При таком соответствии имён формула даёт:
       updaterate=64,  interp=0.015625, ratio=2 -> 0.03125 с (31.25 мс);
       updaterate=128, interp=0.015625, ratio=2 -> 0.015625 с (15.625 мс).
   Это расчёт для указанных входов, а не измерение твоей игры.

4. 0x4333600F–0x433361A9 и записи в 0x43476928: отдельный расчёт сетевой
   задержки. Получается интерфейс через виртуальный вызов +0x138, вызывается
   слот +0x24 с аргументами 0 и 1, имеется обработка истории из 128 элементов,
   результат суммируется. Это соответствует NetChannel/GetLatency по двум
   направлениям в интерфейсной модели Source. 0x43476928 нельзя подписывать
   как lerp: она используется отдельно от результата F.
   Не следует автоматически приравнивать её к client.latency() из Lua:
   семантика двух направлений и дополнительной обработки различается.

5. 0x433AEBA8–0x433AF7C2: выбор кандидатов из кольцевой структуры, обращение
   к индексам с маской 0x1F и временным меткам по +0x4C. Это 32 индексируемых
   слота в данном пути; не утверждение о всех буферах/ёмкостях чита.
   Проверки времени включают отдельную временную величину контекста +0x198,
   сетевой результат и пороги +/-0.2. Смысл всех полей контекста не восстановлен;
   называть +0x198 доказанным полем lerp пока нельзя.

6. 0x433AED1A–0x433AED57: вычисляется сумма квадратов трёх разностей позиций
   и сравнивается с 4096.0 по адресу 0x43472B60, то есть порогом длины 64.
   Подобные проверки есть в 0x43344CD1, 0x43344DDB и 0x43406472.
   Это проверка пространственной непрерывности, а не время интерполяции.
   Afterglow меняет операнд только конкретного участка 0x433AED50 на 512^2;
   остальные сравнения общей константы 4096 автоматически не меняются.

7. 0x43344C0C–0x43345EB7: путь подготовки состояния из истории. Есть копирование
   блока 0x10A0 и смешивание двух записей. В 0x43344E33–0x43344E6E вычисляется
       alpha = clamp((target_time - older_time)/(newer_time - older_time), 0, 1)
   Здесь времена строятся из целочисленных меток и tickinterval.
   0x43344F30–0x43344F73 вычисляет для трёх компонентов по +0x30/+0x34/+0x38:
       output = older + alpha * (newer - older)
   Ещё три компонента смешиваются по +0x0C/+0x10/+0x14. Далее имеются ветки
   преобразований, дополнительные блоки данных и работа с сущностью.
   Нельзя свести всю функцию к перемещению одной точки или считать её полным
   аналогом клиентского CInterpolatedVar: это другой путь подготовки записи.
   Два прямых вызывающих участка: 0x43325ABB и 0x4332FFB1.

8. В участках 0x433AF091/0x433AF167/0x433F9645/0x433F96F3 исходное число 10
   сравнивается с количеством элементов временного списка: разность указателей
   делится на 4. Поэтому ползунок Record Gap в Lua не следует толковать как
   универсальный срок экстраполяции в тиках. Число 128 в 0x433AEE6C и
   0x433F94FD проверяет абсолютную разность вычисленных целочисленных времён;
   это не доказательство буфера на 128 lag records.

9. 0x43468230 содержит начальный integer 200, который в ряде временных функций
   умножается на 0.001. Константа 0.2 используется также отдельно. Эти наблюдения
   не доказывают, что каждая из них является cvar sv_maxunlag, и не доказывают
   жёсткую экстраполяцию противника ровно на 200 мс.

10. Полный путь самостоятельной физической экстраполяции противника вперёд
    с collision trace, гравитацией, обработкой приземления и пересчётом всех
    матриц в этом исследовании не восстановлен. Наличие отдельных смешиваний
    и временных фильтров не доказывает весь такой алгоритм.

ЧТО РАБОТАЕТ ПО УМОЛЧАНИЮ В ОТКРЫТОМ SOURCE SDK (НЕ ПАСПОРТ ТВОЕГО CS:GO)

GetClientInterpAmount берёт максимум cl_interp и отношения cl_interp_ratio
к cl_updaterate. В SDK есть серверные границы ratio; запрос cl_interp также
может учитывать серверный минимум. Нулевой cl_interp не гарантирует нулевой
итоговой задержки. Менять updaterate — не значит менять tickrate сервера.
Источник: https://github.com/ValveSoftware/source-sdk-2013/blob/master/src/game/client/cdll_bounded_cvars.cpp

История переменных привязана к времени симуляции или анимации. Реализация
умеет линейное и Hermite-смешивание; режим зависит от типа и доступной истории.
Когда истории не хватает, экстраполяция требует разрешённого контекста,
подходящих прошлых отсчётов и дополнительных временных условий. Для float/
Vector/QAngle продолжение строится по изменению прошлых значений; это не
универсальный физический симулятор с проверкой стен и пола.
Источник: https://github.com/ValveSoftware/source-sdk-2013/blob/master/src/game/client/interpolatedvar.h

Разрешение экстраполяции контекста связано с cl_extrapolate и паузой движка.
Интерполяция сущностей может отключаться в некоторых режимах и при таймауте.
Источник: https://github.com/ValveSoftware/source-sdk-2013/blob/master/src/game/client/c_baseentity.cpp

Серверная lag compensation отдельно учитывает задержку, lerp в тиках и
sv_maxunlag. В SDK время цели строится из cmd.tick_count минус lerpTicks;
при слишком большом расхождении (0.2 с в этой реализации) применяется
исправление по времени/задержке сервера. Клиентский патч не отменяет этот расчёт.
Источник: https://github.com/ValveSoftware/source-sdk-2013/blob/master/src/game/server/player_lagcompensation.cpp

СЕТЕВЫЕ CVAR И КОМАНДЫ, КОТОРЫЕ НУЖНО РАЗЛИЧАТЬ

Ниже инвентарь относящихся к теме имён Source 1. Некоторые являются скрытыми,
защищёнными, серверными либо отсутствуют в отдельных ветках. Это справочник,
а не набор команд для исполнения и не обещание наличия каждой в твоей игре.

cl_interp                    запрошенная нижняя граница задержки сглаживания.
cl_interp_ratio              коэффициент к интервалу обновлений.
cl_updaterate                запрошенная частота сетевых обновлений.
cl_interpolate               разрешение интерполяции сущностей движком.
cl_extrapolate               разрешение экстраполяции при исчерпании истории.
cl_extrapolate_amount        предел продолжения для пути движка, в секундах.
sv_client_min_interp_ratio   серверный минимум коэффициента.
sv_client_max_interp_ratio   серверный максимум коэффициента.
sv_minupdaterate             серверная нижняя граница частоты обновлений.
sv_maxupdaterate             серверная верхняя граница частоты обновлений.
cl_lagcompensation           клиентский запрос серверной компенсации задержки.
sv_unlag                    серверное включение lag compensation.
sv_maxunlag                 серверное ограничение времени компенсации.
sv_lagcompensation_teleport_dist  порог разрыва позиции в ветках, где доступен.
sv_unlag_fixstuck            проверка застревания при возврате состояния (SDK).
sv_lagflushbonecache         работа кэша костей при серверной компенсации (SDK).

Смежные, но не заменяющие интерполяцию:
cl_cmdrate / sv_mincmdrate / sv_maxcmdrate — частота команд и её ограничения.
rate / sv_minrate / sv_maxrate — ограничения сетевого объёма данных.
cl_predict / cl_predictweapons / cl_pred_optimize — локальный prediction.
cl_smooth / cl_smoothtime — сглаживание исправлений локального prediction.
sv_clockcorrection_msecs — коррекция временной шкалы, если есть в этой ветке.
sv_maxusrcmdprocessticks — обработка команд; это не настройка lerp.
cl_interp_all — обработка списка интерполируемых переменных, не длительность.
cl_interp_npcs — отдельная настройка NPC, не общий регулятор игроков.
cl_interp_threadmodeticks / cl_interp_animationvars — особенности отдельных
веток/режимов; присутствие в твоём CS:GO ещё не подтверждено.

Для чтения/диагностики: help <имя>, cvarlist, find <подстрока>, net_graph,
cl_showerror, cl_predictionlist, cl_pdump, sv_showlagcompensation.
У них разный уровень доступности. net_fakelag/net_fakeloss/net_fakejitter —
искусственные условия теста в поддерживаемых ветках, а не оптимизация стрельбы.

О ЗНАЧЕНИЯХ ПО УМОЛЧАНИЮ

В открытом SDK объявлены ratio=2, cl_interp=0.1, cl_interpolate=1,
cl_extrapolate=1, cl_extrapolate_amount=0.25, cl_predict=1, sv_unlag=1,
sv_maxunlag=1.0. Это defaults SDK. Значения в CS:GO и на конкретном сервере
могут отличаться; переносить эту таблицу в твой конфиг нельзя считать проверкой.
В частности, из SDK нельзя вывести, что твой cl_extrapolate_amount равен 0.25.
Источник объявления лимита экстраполяции:
https://github.com/ValveSoftware/source-sdk-2013/blob/master/src/game/client/interpolatedvar.cpp

Различаются: заводское значение, сохранённое в конфиге значение, текущее значение,
результат ограничивающего getter и приватное значение чита. Одного get_string
или одного get_float недостаточно, чтобы доказать совпадение всех пяти.

Подготовлен отдельный interpolation_probe.lua: он только читает cvar через
публичный API, печатает снимок и сохраняет afterglow_interpolation_audit.txt.
ag_interp_audit повторяет снимок; ag_interp_help запрашивает help для имён.
Он не использует FFI, не пишет cvar, не патчит DLL и не меняет usercmd.
help позволяет увидеть сведения движка о default/flags там, где они доступны;
сам снимок get_float/get_string не выдаётся за чтение заводских defaults.

ПРОВЕРКА ПРИЛОЖЕННОГО lagrecords.gamesense.txt

Это отдельная Lua-библиотека. Её lerp_time — max(interp,ratio/updaterate),
без явных проверок серверных ratio bounds и нулевого updaterate.
Её extrapolate_record ограничивает dt (обычно 0.2 с), сдвигает origin по
скорости/оценке ускорения, но ставит simulation_time в исходный target_time.
При запросе на 1 с вперёд и ограничении 0.2 с координата и временная метка
таким образом могут описывать разные моменты. Эта функция не делает трассировку
столкновений, не задаёт явную гравитацию и не перестраивает матрицы костей
согласно новому положению. Она возвращает Lua-копию; в самом файле её вызовы
не доказывают автоматическую подмену сканируемых скитом записей.
Её TABLE_SIG не найдена точным совпадением в извлечённом binary.bin.
Это не доказывает несовместимость со всеми версиями/памятью процесса, но
использовать её названия полей как подтверждённую схему этой DLL нельзя.

ВЫВОД ДЛЯ ДАЛЬНЕЙШЕЙ РАБОТЫ

Подтверждены самостоятельный расчёт формы lerp, дополнительная временная
граница, отдельный учёт сетевой задержки, отбор записей и смешивание состояний.
Полная замена extrapolation пока не обоснована: не восстановлены все условия,
структуры и связанные матрицы. Следующий недостающий слой — сопоставление
зашифрованных ссылок с реальными cvar и проверка значений/веток в клиенте.
Произвольное увеличение horizon или изменение одной координаты не является
готовой корректной экстраполяцией. Рабочая Lua оставлена прежней.
